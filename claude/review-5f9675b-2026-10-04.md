## Findings

1. **High — a changed SKU/tier/customer price or proof can be used for up to 15 minutes on a Badger invoice.**

   - **File/line:** `apps-script/Code.gs:413-415, 6413-6421, 6529, 6613-6614`
   - **Concrete failure:** `badgerCurrentPrices_()` caches price, invoice volume, and proof for `BADGER_INVOICE_CACHE_TTL_SECONDS` (900 seconds). The only spreadsheet-change triggers are installed for the Outreach and Badger Tracker workbooks—not the Inventory Backend where SKUs, Price Tiers, and Customer Prices live. Both preview and create use the cached result, so a direct correction in the Inventory Backend can leave a reviewer seeing and creating an invoice with the former price or proof. The fingerprint comparison cannot detect it because creation recomputes from the same stale cache.
   - **Suggested fix:** Build the Badger create draft with a fresh catalog read (and make creation reject a fingerprint that changes after that fresh read). Either do the same for preview or label previews as refreshed at creation. Also install an `onChange` invalidation trigger for the actual operational Inventory Backend, in both migration states. Add a test that changes a tier/price/proof between preview and create.

2. **High — conflicting Price Tiers or Customer Prices silently select an arbitrary price for a Badger invoice.**

   - **File/line:** `apps-script/Code.gs:6341-6345, 6379-6385, 6425-6427`
   - **Concrete failure:** duplicate tier rows overwrite the earlier value in the `Map`, while duplicate active customer-price rows are retained and the first matching row is selected. `checkWholesaleCatalog()` does not report either conflict. A duplicate caused by normal sheet maintenance can therefore put the wrong wholesale price on a Badger invoice with no preview-time error.
   - **Suggested fix:** validate normalized tier names and active `(SKU ID, Account ID)` customer-price keys for duplicates/conflicting amounts; include these conflicts in `wholesaleCatalogProblems_()` and block preview/create until resolved. Add duplicate-tier and duplicate-customer-price cases to the workflow tests.

3. **Medium — the four live Squadron products cannot be invoiced because their proofs are blank.**

   - **File/line:** Inventory Backend `SKUs!I38`, `I41`, `I53`, `I68`; enforcement at `apps-script/Code.gs:6360-6365, 6534-6539`
   - **Concrete failure:** Flying Fortress Bourbon, Hellcat Rum, Mustang Moonshine, and Spitfire Gin correctly use the `Squadron` tier, and that tier is $40, but all four have no proof in the SKUs tab. They are emitted with proof `0`, then every Badger invoice draft containing one is blocked. This fails safe (it will not send a wrong proof), but prevents invoicing an otherwise active product.
   - **Suggested fix:** enter the approved proof for each of these rows before any approval/activation that relies on Badger invoicing. Keep the draft’s proof check; add a live catalog preflight to the approval workflow so the block is found before an order reaches invoicing.

4. **Medium — a SKU missing from the newest Toast report retains its old stock and can remain publicly “In stock.”**

   - **File/line:** `apps-script/Code.gs:6274-6285, 6315-6327, 1126-1140`
   - **Concrete failure:** `toastStockUpdates_()` reports mapped SKUs absent from the report, but `importLatestToastStockReport()` writes only `result.updates`. The old `toast_stock` and date remain in SKUs. `apiListSkus_()` does not assess stock age, so an omitted/discontinued item can continue to be shown as “In stock” from a previous report.
   - **Suggested fix:** for a mapped SKU absent from a successfully parsed report, clear the stock value/date or set a distinct “availability needs confirmation” state; do not infer zero. Make `apiListSkus_()` treat missing or stale report dates as confirmation-needed, and test this exact transition.

5. **Low — the catalog checker reports valid bitters as Toast-mapping defects.**

   - **File/line:** `apps-script/Code.gs:6391-6403`
   - **Concrete failure:** every active SKU with no `toast_item_name` is placed in `no_toast_item`. The live 50 mL, 180-proof bitters rows intentionally have no Toast stock because they are Toast modifiers. Thus the checker’s output contains expected business data as an apparent catalog problem, obscuring real missing mappings.
   - **Suggested fix:** add an explicit stock-tracking field/enum (for example, `toast_stock_mode = tracked | modifier | not_applicable`) and require `toast_item_name` only for `tracked`; cover bitters in the catalog-check test.
